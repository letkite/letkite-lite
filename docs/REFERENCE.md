## File layout

### Gateway

```
/opt/vpsmcp/                       vpsmcp:vpsmcp 750
  .venv/                           virtualenv
  src/vpsmcp/                      installed source
  .rollback/<timestamp>/           last 3 pre-upgrade snapshots

/etc/vpsmcp/                       root:vpsmcp 750    service can read, not write (except hosts.d/)
  vpsmcp.env                       root:vpsmcp 640    all settings
  id_ed25519                       root:vpsmcp 640    fleet private key
  id_ed25519.pub                   root:vpsmcp 644
  known_hosts                      root:vpsmcp 644
  hosts.yaml                       root:vpsmcp 640    hand-written entries
  hosts.d/                         vpsmcp:vpsmcp 750  service-writable
    n_<hash>.yaml                  vpsmcp:vpsmcp 640  one enrolled node each

/var/lib/vpsmcp/                   vpsmcp:vpsmcp 750
  oauth_signing_key.pem            600  RS256 key for access tokens
  cookie.key                       600  login session signing key
  oauth.db                         600  clients, refresh tokens, node registry
  audit.jsonl                      600  one JSON record per tool call

/etc/systemd/system/vpsmcp.service written by `vpsmcp setup` (reference copy: deploy/vpsmcp.service)
/usr/local/bin/vpsmcp              wrapper: sudo -u vpsmcp ... -m vpsmcp (`setup` runs as root)
/etc/caddy/Caddyfile               generated by `vpsmcp caddyfile`
```

`/etc/vpsmcp` stays root-owned on purpose: a compromised service process can read
the fleet key (it must, to connect) but cannot replace it, and cannot rewrite
`vpsmcp.env`. Only `hosts.d/` is writable by the service, because enrollment
writes there. The systemd unit enforces this with `ReadOnlyPaths=/etc/vpsmcp` and
`ReadWritePaths=/var/lib/vpsmcp /etc/vpsmcp/hosts.d`.

### Node

```
/home/<user>/.ssh/authorized_keys  <user>:<user> 600  gateway public key appended
/home/<user>/.vpsmcp/jobs/<job_id>/                   detached job state
  cmd.b64  meta.json  pid  pgid  stdout.log  stderr.log  exit_code
/etc/ssh/sshd_config.d/60-vpsmcp-<user>.conf          only if pubkey auth was off
```

Nothing else. No code, no private key, no certificate.

## Users and groups

| Account | Where | Shell | Purpose |
|---|---|---|---|
| `vpsmcp` | gateway | nologin | system account the daemon runs as; owns `/opt/vpsmcp`, `/var/lib/vpsmcp`, `/etc/vpsmcp/hosts.d` |
| `ops` (`VPSMCP_ENROLL_USER`) | every node | `/bin/bash` | account the gateway logs in as; no password, no sudo |
| `caddy` | gateway | nologin | created by the Caddy package |
| your login user | gateway | — | admin; only needs sudo |

The node account is created with `useradd -m`, then `usermod -p '*'`. `useradd`
leaves `!` in `/etc/shadow`, which hosts configured with `UsePAM no` treat as a
locked account and refuse even key-based logins.

Do not add the node account to `sudo`/`wheel`. The whole permission model rests
on it being unprivileged. If a specific privileged action is needed, allowlist
exactly that command:

```
ops ALL=(root) NOPASSWD: /bin/systemctl reload nginx
```

and set `sudo: true` on that host in the inventory.

## Keys and certificates

| Item | Location | Type | Rotation |
|---|---|---|---|
| Fleet SSH key | `/etc/vpsmcp/id_ed25519` | Ed25519, no passphrase | manual; replacing it orphans every enrolled node |
| Node host keys | inventory `host_key` | reported at enrollment, pinned | re-enroll the node |
| OAuth signing key | `/var/lib/vpsmcp/oauth_signing_key.pem` | RSA 2048, RS256 | replacing it invalidates live access tokens; clients recover on refresh |
| Cookie key | `/var/lib/vpsmcp/cookie.key` | 32 random bytes | replacing it logs you out of the consent page |
| TLS certificate | `/var/lib/caddy/.local/share/caddy/certificates/` | issued by Caddy | automatic, renewed ~30 days before expiry |

The SSH key has no passphrase because systemd cannot answer a prompt. It is
generated in-process during setup and written straight to disk.

TLS uses HTTP-01 by default, so port 80 must be reachable. If it is not, use
DNS-01: `vpsmcp caddyfile --dns-route53 <zone-id>`, a Caddy build with the
provider plugin, and credentials in a systemd drop-in (not in the Caddyfile,
which is world-readable).

## Ports

| Port | Listener | Exposure |
|---|---|---|
| 443 | Caddy | public |
| 80 | Caddy | public, ACME HTTP-01 only |

## HTTP endpoints

| Path | Auth | Caller |
|---|---|---|
| `/mcp` | Bearer JWT | the client |
| `/.well-known/oauth-protected-resource[/mcp]` | none | the client |
| `/.well-known/oauth-authorization-server`, `/.well-known/openid-configuration` | none | the client |
| the same two with `/mcp` inserted or appended (RFC 8414 path forms) | none | clients that treat the resource URL as the issuer |
| `/oauth/register` | none (DCR) | the client |
| `/oauth/authorize`, `/oauth/login` | password | your browser |
| `/oauth/token`, `/oauth/revoke`, `/oauth/jwks.json` | per spec | the client |
| `/enroll/pubkey`, `/enroll/register` | enrollment gate | new nodes |
| `/enroll/install.sh`, `/enroll/uninstall.sh` | none (scripts hold no secret) | nodes |
| `/enroll/deregister` | none; a node can only remove itself (source IP + user + port) | nodes |
| `/healthz` | none | monitoring |

`--lock-anthropic` restricts the endpoints only the Anthropic backend calls to
its egress range. It must not cover `/oauth/authorize`, `/oauth/login` or
`/enroll/*`, and must not be used at all with Claude Code, which connects from
your own machine. It also blocks Kimi and GLM, whose egress ranges are not
published; add networks you know with `vpsmcp caddyfile --allow-cidr <cidr>`
(repeatable), or leave the lock off.

## Clients

A client is accepted when its OAuth callback matches the allowlist. Everything
else in the flow is identical for all of them, so the client list is a list of
callbacks:

| `VPSMCP_CLIENTS` key | Client | Callbacks |
|---|---|---|
| `claude` | Claude | `https://claude.ai/api/mcp/auth_callback`, same on `claude.com` |
| `local` | Claude Code, MCP Inspector | `http://localhost/callback`, `http://127.0.0.1/callback`, any port (RFC 8252 §7.3) |
| `kimi` | Kimi (Moonshot AI) | `kimi.com`, `www.kimi.com`, `kimi.moonshot.cn`, `www.kimi.moonshot.cn`, `platform.moonshot.cn`, `platform.moonshot.ai` |
| `glm` | GLM (Zhipu AI / Z.ai) | `chat.z.ai`, `z.ai`, `chatglm.cn`, `www.chatglm.cn`, `open.bigmodel.cn`, `bigmodel.cn` |

Claude publishes a fixed callback path, so its entries are exact. The Kimi and GLM
entries are host-scoped (`https://<host>/` matches any path on that host) because
those vendors do not document theirs and may change it. A host-scoped entry means
trusting that host not to run an open redirect; the consent page therefore names
the callback host and the client it belongs to before you approve.

```bash
sudo vpsmcp clients [--json]          # profiles, on/off, callbacks
sudo vpsmcp redirects [--json]        # effective allowlist + refused callbacks
sudo vpsmcp redirect allow <uri>      # add one (https, or http on loopback)
sudo vpsmcp redirect deny  <uri>      # remove one added this way
sudo vpsmcp redirect clear-rejected   # forget the refusal list
```

Entries added with `redirect allow` live in `oauth.db`, are read on every
request (no restart) and are listed as "added by hand". Refused callbacks are
recorded - with the client name it registered under - so a new client is allowed
by copying its URL rather than guessing it. That list is written by
unauthenticated requests, so it holds at most 200 distinct URLs and forgets
entries after 30 days.

The three sources are merged: client profiles (`VPSMCP_CLIENTS`),
`VPSMCP_ALLOWED_REDIRECTS`, and the runtime entries. To make the env variable the
whole allowlist, set `VPSMCP_CLIENTS=` empty.

## Settings

All read from `/etc/vpsmcp/vpsmcp.env` (override the path with `VPSMCP_ENV_FILE`). Values are single-quoted because the
password hash contains `$`.

| Variable | Default | Notes |
|---|---|---|
| `VPSMCP_PUBLIC_URL` | — | bare domain, no path |
| `VPSMCP_MCP_PATH` | `/mcp` | resource URL = public_url + this |
| `VPSMCP_BIND_HOST` / `_PORT` | `127.0.0.1` / `8848` | |
| `VPSMCP_TRUSTED_PROXY_HOPS` | `1` | reverse proxies in front of the app; the client IP is taken this many entries from the right of `X-Forwarded-For`. `1` for one Caddy/nginx (the default setup), `2` behind a CDN or load balancer that also appends, `0` if the app is bound to a public port with no proxy (the header is then ignored). Getting this wrong does not expose data, but too high trusts a forged prefix and too low buckets every caller under the proxy |
| `VPSMCP_PROXY_ENABLE` | `0` | run the egress forward proxy (`vpsmcp proxy` / `vpsmcp-proxy.service`) |
| `VPSMCP_PROXY_PORT` / `_BIND_HOST` | `8443` / `0.0.0.0` | where the egress proxy listens |

## Egress proxy (optional)

Nodes can route their outbound HTTP(S) through the gateway, giving the fleet one
stable egress IP. It is off by default.

**Gateway** — set a credential and start the service:

```bash
sudo vpsmcp proxy-password                 # sets VPSMCP_PROXY_PASS_HASH, enables it
sudo systemctl enable --now vpsmcp-proxy   # listens on :8443
```

The proxy requires `Proxy-Authorization: Basic` on every request and refuses any
destination that resolves to a private / loopback / link-local / reserved address
(resolved once and pinned), so a node holding proxy creds cannot reach the
gateway's own `127.0.0.1:8848`, its SSH, cloud metadata, or the internal network -
only the public internet. Terminate TLS on the proxy port (`VPSMCP_PROXY_TLS_CERT`
/`_KEY`) so the Basic credential is not sent in clear.

**Node** — opt in at enrollment, then toggle per account:

```bash
curl -sSf https://mcp.example.com/enroll/install.sh | sudo bash -s -- \
     --alias hk-main --proxy 'http://node:PASS@mcp.example.com:8443'
vpsmcp-proxy status        # gateway | system
vpsmcp-proxy off           # switch back to the node's system proxy
vpsmcp-proxy on            # back to the gateway proxy
```

`--proxy` writes `~/.vpsmcp/proxy.sh` for the node account and sources it from that
account's shell rc (per-account, not system-wide); egress is active on deploy and
`vpsmcp-proxy` flips between the gateway proxy and the system default.

## Scopes

| Scope | Grants |
|---|---|
| `fleet.read` | list hosts, host facts, read files, list dirs, logs, job status, gateway status |
| `fleet.exec` | exec, exec_many, shells, start/stop jobs |
| `fleet.write` | write, delete, copy files, purge job dirs |
| `fleet.admin` | port forwarding, audit log |

Effective permission is the intersection of token scope, the host's scopes in the
inventory, and what the SSH account can actually do. Only the last is a hard
boundary. Note that `fleet.exec` implies write in practice - a shell can redirect
into a file - so the read/write split only means something for hosts that do not
grant exec.

A `session_id`, `sub_id` or `tunnel_id` is a handle, not a capability: `shell_run`,
`log_read` and `tunnel_http` check the caller's token against the host the handle
belongs to, as the tool that opened it did. Another token that learns the id gains
nothing it did not already hold, and withdrawing a scope from a host (or removing
the host) also stops the shells, logs and tunnels already open on it.
